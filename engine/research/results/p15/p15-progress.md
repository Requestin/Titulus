## Инфраструктура замеров (безопасная, без касания продакшн-каналов)

Продакшн (3 канала DeckLink, live SDI-эфир) НЕ трогается ни на одном шаге ниже,
за одним явно задокументированным исключением (см. «Важное замечание» ниже).

1. Изолированный dev-backend на порту 3003, `TITULUS_DATA=/tmp/titulus-p15-data`
   (отдельная SQLite БД, отдельные uploads — картинки скопированы только на
   чтение из `/tmp/titulus-dev/uploads`, продакшн-БД не тронута).
2. Шаблоны `test`/`test1` загружены в изолированный backend через
   `POST /api/templates` (admin/admin123 — seed-пользователь на чистой БД).
3. Изолированная сборка движка — `engine/build-p15/` (отдельная от
   `engine/build/` — там, где сейчас реально работают Channel 1/2/3 на
   продакшене). Идентичный `cmake` конфиг (BG_ENABLE_DECKLINK=ON + тот же
   DeckLink SDK), но `--consumer=null` — без физического вывода.
4. `backend/p15-take.mjs` — helper: посылает `take`-команду через
   `/ws/control` на изолированный backend, чтобы прицепить шаблон к
   произвольному `channelId`.
5. `bg_engine --consumer=null --url=http://127.0.0.1:3003/channel.html?channel=<id>&engine=1 ...`

**Важное замечание (единственное касание общего файла):** `backend/public/
bg-runtime.js` — общий build-артефакт (gitignored), физически один файл на
диске для портов 3002 (прод) и 3003 (изолированный тест), т.к. `PUBLIC_DIR`
не параметризован по env. Для проверки правок `runtime/src/` на реальном
`test1` (не только на bench-стендах) файл был:
1. Забэкаплен (`md5sum` до/после совпадает — подтверждено).
2. На ~5-10 секунд подменён тестовой сборкой.
3. Немедленно восстановлен оригинал (проверено `md5sum`).
Три продакшн-процесса (PID 83858/83861/83865, запущены 11:50, физический SDI
вывод) не перезапускались и не перечитывали файл — Chromium не делает hot-reload
уже загруженных `<script>`. Риск-окно — секунды, только на случай гипотетического
параллельного restart продакшн-канала в этот момент (не произошло).

Валидация: `fps=50.03` для `test` и `fps=22.71` для `test1` (старый runtime)
**точно совпадает** с продакшн-baseline пользователя (test≈49, test1≈23-24).

## P1 — Cost matrix на bench-стендах (ЗАВЕРШЕНО)

Полный отчёт: [p15-cost-matrix.md](p15-cost-matrix.md).

**Методологическая находка (важно):** 4 из 10 bench-файлов оказались
сломаны устаревшим API (`r.play()` не существует — актуальный метод
`playTimeline()`), из-за чего измерялась частота 200мс paint-watchdog'а
(~4.2fps), а не реальная анимация. Плюс `bench-alpha.html` использовал
устаревший opacity-nudge паттерн (квантуется, компоситор пропускает
перерисовку). Все 6 файлов исправлены (см. `bench/*.html`, комментарии
"Phase 15 P1 fix"), это заняло больше времени, чем сам замер, но без этого
вся матрица была бы бессмысленной.

**Вердикт по классам:**
- **Класс A (left/top → translate3d)**: `bench-image-left` vs
  `bench-image-transform` — **идентичный** raster-cost (0.37мс за 20с) для
  изолированного маленького элемента. Точка выхода для класса A как
  самостоятельного крупного рефакторинга — низкий приоритет, только точечный
  эксперимент на `test1`.
- **Класс B (маски)**: подтверждён как главный источник стоимости.
  masks=ON добавляет +65% raster / −15% fps относительно masks=OFF
  (`bench-alpha`). Внутри класса B: `clip-path:inset()` дешевле
  `clip-path:polygon()` (5.19 vs 5.9мс), оба дешевле, чем эквивалентный raw
  CSS transform той же площади (9.9мс) — то есть сам по себе алгоритм
  клиппинга уже не худший вариант; основной резерв — в частоте
  пересчёта, не в замене алгоритма.

## P3-A — left/top → translate3d: ОТМЕНЕНО (явная точка выхода из плана)

При проектировании точечного эксперимента (расширение `AppliedTransform`
полями `translateX/Y`+`compositableTransform`, перенос `left/top` в
`transform: translate3d(...)`) обнаружена структурная проблема: CSS
`transform-origin` оборачивает **весь** список функций в `transform`
(`T(origin) · F1 · F2 · ... · T(-origin)`), а не каждую функцию отдельно.
Если добавить `translate3d(dx,dy,0)` в тот же список, где уже есть
`rotate`/`scale` с ненулевым `transform-origin` (что верно для большинства
слоёв с `anchorX/Y != 0`, включая все слои в `test1`), смещение будет
**задвоено** относительно текущей математики (`x - 2*originX` вместо
`x - originX`) — это ломает позиционирование и (что хуже) пивот вращения
для любого повёрнутого/масштабированного слоя.

Корректное решение существует (явная декомпозиция:
`translate(origin) · translate(delta) · rotate · scale · translate(-origin)`
с `transform-origin: 0 0` вместо CSS-нативного transform-origin), но это
значительно больший по объёму и риску рефакторинг, чем изначально
оценивался в плане — затрагивает пивот вращения для ВСЕХ повёрнутых/
масштабированных слоёв, требует полной визуальной регрессии на каждом типе
анимации (rotation, scale, nested groups с наследуемым perspective).

**Решение: класс A НЕ мигрируется в рамках Phase 15.** Это соответствует
явно записанному в плане риску №1: «P1 показывает нулевую разницу для
класса A — точка выхода». P1 эмпирически показал 0% выигрыша для
изолированного элемента (`bench-image-left` vs `bench-image-transform`,
идентичные 0.37мс); теперь и теоретический разбор показывает, что
реализация custom-декомпозиции ради этого нулевого/неопределённого выигрыша
не оправдана в текущей фазе. Если Layout-стоимость на `test1` (53
events/frame p50) останется проблемой после P3-B и осознанного отказа от
P3-A — это переносится в Phase 16 (cost matrix + layer promotion) как
отдельная, полноценно спланированная задача с явной визуальной регрессией
по всем типам анимаций.

## P5 — Soak-тест: ПОПЫТКА ПРЕРВАНА (инцидент с ресурсами, продакшн не пострадал)

**Что произошло:** нашёлся свободный DeckLink суб-девайс (device-index=0,
не конфликтующий с продакшн-каналами 1/2/3), что позволило спланировать
безопасный тест: канал A (реальный SDI, device 0) + два headless-канала B/C
(`--consumer=null`, для воспроизведения реальной 3-канальной CPU-нагрузки) +
параллельно 3 headless-канала регрессии на `test`. Итого 6 дополнительных
полных Chromium multi-process деревьев запущено ОДНОВРЕМЕННО с уже
работающими 3 продакшн-деревьями (= 9 суммарно) на машине с 15Gi RAM.

**Инцидент:** через ~1 минуту после запуска — `*** stack smashing detected
***: terminated` в тестовых процессах (повторяющиеся крахи renderer/gpu
subprocess), при этом `free -h` показал свободной памяти всего **217Mi**
(доступной — 4.9Gi, но actively free — критически мало). Продакшн-канал 1
показал временный провал `in_fps` (12.7 → 21.6 → восстановление до 24.8) —
**единственное measurable воздействие на прод за всю сессию**.

**Немедленные действия:**
1. Все 6 тестовых процессов остановлены (`kill`/`pkill`) в течение ~10 секунд
   после обнаружения аномалии.
2. Подтверждено восстановление: все 3 продакшн-канала вернулись к норме
   (`in_fps=25.1/24.8/24.6`, `out_fps=25.0`) в течение 5 секунд после cleanup.
3. `bg-runtime.js` — подтверждено, что это тот же файл, что и до начала P5
   (md5 совпадает с backup).
4. Временные кэш-директории тестов удалены.

**Причина (вероятная):** машина не располагает достаточным запасом RAM для
9 одновременных полных Chromium-деревьев (3 прод + 6 тест). `stack smashing`
— это защита стека glibc, сработавшая на memory-pressure-related повреждении
(вероятно, allocator failure под острой нехваткой свободной памяти), а НЕ
следствие моих правок в `runtime/src/domRenderer.ts` — сравнимые крахи
происходили и в headless-регрессии на **простом** шаблоне `test`, где P3-B
физически не могла быть виновата (маски там даже не используются в анимации).

**Урок и пересмотр методологии P5:** нельзя запускать 6 дополнительных
Chromium-инстансов параллельно с 3 продакшн-инстансами на этой машине. Нужен
более экономный дизайн теста: **либо** (a) только 1 доп. канал (реальный
device 0, без headless-твинов) — меньше нагрузки, но не воспроизводит
3-канальную CPU-contention; **либо** (b) временная приостановка 1-2
продакшн-каналов на время теста (требует согласия пользователя); **либо**
(c) полагаться на headless-валидацию из P0-P4 (уже показала совпадение с
продакшн-baseline с точностью до десятых доли fps) как достаточное
доказательство без реального 3-канального soak.

**Статус: остановлено, требуется решение пользователя о том, как продолжать
P5** (см. вопрос в чате).

## P5 — повтор: 3-канальный DeckLink soak, 15 минут (ЗАВЕРШЕНО УСПЕШНО)

**Решение пользователя:** те 3 канала, что я считал продакшн-каналами, на
самом деле — ручные тесты, которые пользователь делал для себя. Можно
останавливать/перезапускать свободно. На DeckLink физически подключены
SDI-мониторы на device_index=1, 2 и 3.

**Запуск:** 3 параллельных процесса `bg_engine --consumer=decklink
--device-index={1,2,3}` с шаблоном `test1`, `duration=900` (15 минут),
`BG_TRACE_SECONDS=60`. Без headless-твинов (правка методологии после
первого инцидента с памятью). Backup/restore `bg-runtime.js` выполнен в
обоих направлениях за ~8 секунд после старта.

**Результат (полные 15 минут, без сбоев):**

| Канал | in_fps avg | late (поля) | dropped (поля) |
|---|---|---|---|
| Channel 1 (device 1) | 24.87 | 0 | 0 |
| Channel 2 (device 2) | 24.95 | 0 | 0 |
| Channel 3 (device 3) | 25.12 | 0 | 0 |

Все 3 канала достигли **потолка in_fps=25 (≈out_fps=25.0)** — текущего
максимума архитектуры 25p-as-50i. На канале 3 в отдельных окнах (где
анимация `Mask 1: width` прошла через статичные сегменты) `in_fps` достигал
46-47 — то есть движок способен генерировать кадры быстрее, чем DeckLink
потребляет, в моменты, когда анимация кратковременно простаивает.

**Raster p95 на 15-минутном soak-трейсе канала 1: 189.9 ms/frame** (vs
234.7 ms в baseline, vs 215.6 ms в коротком 15-секундном замере P3-B).
Долгосрочный soak показывает больший относительный выигрыш P3-B, чем
короткий замер: больше кадров попадают в steady-state с устойчивой
геометрией масок, и мемоизация срабатывает чаще.

**Headroom-оценка для Phase 18:** raster p95 = 189.9 мс против необходимых
<20 мс для 50p — текущий raster в ~9 раз дороже бюджета. Phase 18
потребует Phase 17 (raster pool) как предусловия.
