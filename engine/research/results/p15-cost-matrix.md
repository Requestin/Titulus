# Phase 15 P1 — Cost matrix (bench stands, headless, `--consumer=null`)

Дата: 7 июля 2026. Все прогоны — 20с headless, идентичная сборка
(`engine/build-p15/`), без касания продакшн-каналов.

## Методологическая находка (важно!)

При первом прогоне 4 из 10 bench-файлов (`bench-image-left`,
`bench-wipe-inset`, `bench-wipe-polygon`, `bench-mask-stack`) показали
аномальные `~4.2 fps` — это оказался не реальный сигнал, а артефакт:

1. **API drift**: эти файлы вызывали `r.syncTemplate(tpl,{}); r.play();`,
   но текущий `TemplateRenderer` ([runtime/src/domRenderer.ts](../../src/../../../runtime/src/domRenderer.ts))
   больше не имеет метода `.play()` — playback теперь единый вызов
   `playTimeline(template, variables)`. `r.play()` бросал `TypeError`,
   который убивал весь остальной код в IIFE (включая heartbeat/beacon),
   поэтому страница вообще не производила compositor damage кроме
   200мс-watchdog fallback в `main.cpp` (`Paint watchdog: ... nudge ONE
   refresh` — engine/src/main.cpp:361-373). Т.е. замерялась частота
   watchdog'а, а не сцены. **Исправлено**: заменено на `r.playTimeline(tpl, {})`
   в 4 файлах.
2. **Устаревший opacity-nudge** в `bench-alpha.html`
   (`stage.style.opacity = 0.999 + random*0.001`) — именно тот
   анти-паттерн, который комментарий в `channel.html` (§10) описывает как
   уже отвергнутый: значение квантуется в тот же 8-битный alpha большинство
   кадров, компоситор решает, что урона нет, и не перерисовывает.
   Результат — не 50fps, а ~25-28fps (частота watchdog'а/случайных попаданий
   в другое квантованное значение). **Исправлено**: заменено на тот же
   beacon-паттерн (toggle цвета 1×1px div), что и в остальных bench.
3. Добавлен defensive beacon в `bench-25d.html` (не изменил результат —
   3D-стоимость там реальна, не артефакт).

Все правки — в `bench/*.html`, задокументированы инлайн-комментариями
с префиксом "Phase 15 P1 fix". Одно исключение (`bench-alpha.html`) добавлено
в `.impeccable` ignore-list (design-hook ложно сработал на «один шрифт для
всей страницы» — это internal performance-test fixture, не пользовательский UI).

## Вердикты по классам

### Класс A (left/top → translate3d на layer/group): **НЕ ПОДТВЕРЖДЕНО, низкий приоритет**

`bench-image-left` и `bench-image-transform` дали **идентичный** raster-cost
(0.37ms за 20с) для одного маленького (640×360) изображения. В данном
CPU-only OSR (без GPU-compositor'а) миграция позиционирования с `left/top`
на `translate3d` **не показала измеримого выигрыша** для изолированного
элемента такого размера.

Это соответствует риску №1, заранее описанному в плане Phase 15: «P1
показывает нулевую разницу для класса A — точка выхода для класса A».
**Однако** это не окончательный вердикт для `test1` — там десятки слоёв
одновременно анимируются по x/y, и Layout может быть дороже при большем
количестве одновременных изменений (Layout — это, в отличие от Raster,
часто дороже при большом числе элементов в общем дереве, а не при размере
одного элемента). Решение: **не мигрировать класс A изолированно ради самого
факта миграции**; вместо этого измерить Layout-стоимость непосредственно на
`test1` до и после точечного P3-A прогона (дешёвый, обратимый эксперимент),
а не как самостоятельный крупный рефакторинг.

### Класс B (маски: clip-path/maskImage): **ПОДТВЕРЖДЕНО — главный приоритет**

Маски показывают явную, измеримую, растущую с сложностью стоимость:

- Один статический wipe (inset/polygon) — 5-6мс за 20с.
- Два маски + анимация — 21мс (>2x одного).
- `bench-alpha` masks=ON добавляет **+106мс raster** (+65%) и **−15% fps**
  относительно masks=OFF — прямое подтверждение того, что маски — не
  бесплатны и масштабируются с количеством/сложностью.

Это согласуется с P0 baseline: `test1` (сложный, с масками) показал raster
p50=172.6мс/кадр против `test` (без масок) — 1.85мс/кадр, разница **93x**.

**Вывод: класс B (маски) — главный кандидат оптимизации Phase 15,** не класс
A. Внутри класса B: `clip-path: inset()` (5.19мс) дешевле, чем
`clip-path: polygon()` (5.9мс) — ожидаемо, т.к. polygon требует пересчёта
точек многоугольника на JS-стороне (`maskGeometry.ts:projectMaskOutline`)
каждый кадр при анимации, тогда как inset — чистый CSS.

Интересно: `bench-wipe-transform-only` (raw CSS transform БЕЗ clip-path,
большая площадь) дал **9.9мс — дороже**, чем оба mask-based варианта (5.19 и
5.9мс)! Это означает, что сама by-себе площадь перекрашиваемого региона
(800×650px, двигающегося) стоит больше, чем clip-path пересчёт для
сопоставимой площади. Это ценная находка: **раз clip-path-подходы (inset,
polygon) уже ДЕШЕВЛЕ эквивалентного raw-transform для той же геометрии**,
переписывание масок на `transform: scaleX` (Algorithm 3 из первоначального
плана) **не гарантированно окажется быстрее** — этот путь всё равно двигает/
масштабирует контент, что и создаёт raster-нагрузку. Приоритет для P3-B
следует отдать не смене алгоритма клиппинга, а **минимизации частоты
пересчёта** (кэширование `clipGeoKey`, пропуск пересчёта на неизменной
геометрии) и **уменьшению области инвалидации**.

### Класс C/D: не тестировались отдельно в P1 (bench-файлов для них нет)

`test1` не анимирует `background`/`textShadow`/`fontSize` кадр-в-кадр по
данным P0 (baseline не показал заметного вклада paint.paint относительно
raster.task — 815мс paint vs 20722мс raster за 15с трейс, разница 25x). P3-C/D
откладываются как низкоприоритетные — фокус P3 на класс B, с точечной
проверкой класса A.

## Что это значит для P3

Приоритет P3 меняется относительно первоначального плана:

1. **P3-B (маски) — первым и главным**: не менять алгоритм клиппинга
   вслепую, а (a) убедиться, что `cache.clipGeoKey`
   ([domRenderer.ts:694](../../src/../../../runtime/src/domRenderer.ts))
   реально предотвращает пересчёт на статичной геометрии, (b) для
   axis-aligned масок (без rotation) — предпочесть `inset()` над `polygon()`
   там, где это возможно (уже дешевле по данным матрицы), (c) измерить
   реальный вклад на `test1` до/после.
2. **P3-A (left/top → translate3d) — точечный эксперимент, не крупный
   рефакторинг**: попробовать на `test1` напрямую (не изолированно на bench),
   измерить Layout events/frame до/после; если эффект в пределах шума —
   откатить эту часть, не тратя время на класс C/D.
3. **P3-C/D — низкий приоритет**, только если P0/P3 замеры на `test1`
   покажут значимый вклад после устранения класса B.
