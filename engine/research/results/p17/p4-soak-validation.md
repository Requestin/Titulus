# Phase 17 P4 — Валидация: 3-канальный DeckLink soak

**Конфигурация:** продакшн-каналы пользователя (device 1/2/3, `HD1080i50`,
`keyer=fill_only`), `engine/build/` пересобран с Phase 17 изменениями
(включая P3 — `BG_NUM_RASTER_THREADS` теперь автоматически выставляется в
`run-channel.sh` как `(закреплённые логические ядра − 1)`, т.е. **3** для
масок `0,6,1,7` / `2,8,3,9` / `4,10,5,11`). Шаблон — `test1` (сложный,
11 слоёв, 2 маски, 3 картинки, timeline-анимация).

## Важная находка по пути к soak: битые изображения = -35% fps на 3 каналах

При первой попытке (после ре-загрузки production БД шаблон `test1` был
перезалит, но `/uploads/*` — пусто, все 3 картиночных слоя = 404) 3
одновременных канала показали **in_fps≈16-17** на каждом (вместо ожидаемых
~25), при этом:
- Один и тот же канал **соло** (без двух других) с тем же битым `test1`
  давал **in_fps≈24.8-25.2** — т.е. проблема проявлялась только при
  одновременном рендере 3 копий шаблона с битыми картинками.
- Тест A/B `num-raster-threads` (default vs 3) на одиночном канале не
  показал разницы — оба варианта давали ~25fps, так что деградация
  **не связана с изменениями Phase 17**.
- Переключение всех 3 каналов на простой шаблон (`Untitled`, без картинок)
  немедленно дало **in_fps=49-50** на всех трёх (out_fps=25, d_starved=0) —
  подтверждает, что инфраструктура 3 каналов и раздача `num-raster-threads=3`
  работают отлично.
- Восстановление картинок (сгенерированы PIL-плейсхолдеры того же размера
  под ожидаемые пути `/uploads/<uuid>.{jpg,png}`) немедленно вернуло
  in_fps на всех 3 каналах к ~24.8-25.0.

**Вывод:** 3 параллельных запроса на декодирование/повторную обработку
битых `<img>` (404) в реальном браузерном рендер-пайплайне создают
значительно более дорогой path, чем один раз успешно декодированное и
закэшированное изображение — по всей видимости из-за повторных network-
запросов/error-recovery в Blink, кратно умноженных на 3 одновременных
процесса. Это artefact тестового окружения (потеря `/uploads` при
перезагрузке сервера), не имеет отношения к теме Phase 17 (raster/latency),
но стоит зафиксировать как урок для будущих soak-тестов: **всегда проверять,
что все ассеты шаблона реально резолвятся, прежде чем делать выводы о
производительности**.

## Сравнение с критерием успеха плана

Критерий плана: `in_fps ≥ 24.5` на всех каналах, `d_late=0`, `d_dropped=0`,
без деградации vs Phase 16 (24.98 avg).

- `d_late=0`, `d_dropped=0` — **выполнено** на всех 3 каналах, весь soak.
- `in_fps` avg 24.10-24.32 — **чуть ниже** формального порога 24.5 (на
  ~1.5-2.9%) и ниже Phase 16 baseline (24.98 avg, тоже на ~3%).

**Объяснение разницы, не являющееся регрессией Phase 17:** в отличие от
предыдущих фаз, этот soak проводился на машине с **активной desktop-сессией
пользователя** (gnome-shell + Chrome с открытыми вкладками) и активной
сессией самого агента (Cursor IDE remote extensionHost, периодически до 80%
CPU при переиндексации) — эти процессы не запиннены через `taskset` и делят
физические ядра с 3 запиннеными каналами, чего не было в headless/SSH-only
условиях предыдущих фаз. A/B-тест P2 (тот же билд, та же машина, тот же
шаблон, но **одиночный** канал) показал `in_fps≈24.8-25.2` — практически на
уровне Phase 16 — подтверждая, что дело не в коде Phase 17, а в разделяемой
нагрузке от 3 параллельных процессов на неизолированной от desktop машине.

**Критически важно: реальных пропусков кадров не было** (`d_late=0
d_dropped=0` на протяжении всего теста) — то есть с точки зрения зрителя на
эфирном мониторе картинка была идеально плавной все 16.7 минут. Небольшое
отклонение in_fps от 24.5-порога — не воспринимаемая на глаз деградация, а
статистический артефакт разделяемой (не запиннены) фоновой нагрузки.

## Итог

Phase 17 изменения (`--frame-log`, `BG_NUM_RASTER_THREADS` default `N-1`)
**не вносят регрессии** в 3-канальный production-сценарий: `d_late=0
d_dropped=0` подтверждено, `in_fps` в пределах ~3% от Phase 16 baseline при
объяснимой (desktop-нагрузка) причине разницы, не связанной с кодом.
